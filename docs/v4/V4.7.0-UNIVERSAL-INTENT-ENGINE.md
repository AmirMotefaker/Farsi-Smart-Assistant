# v4.7.0 — Universal Intent Engine

## Product goal

Farsi Smart Assistant must not behave like a fixed lookup table.

The runtime must be able to infer wrong-layout intent for words it has never
seen as exact dictionary entries.

Golden examples:

- `\\sv -> پسر`
- `ذخغ -> boy`
- `زشف -> cat`
- `یخل -> dog`

## Architecture

### Candidate generation

For every eligible token the engine can compare:

1. original token
2. physical English-keyboard -> Persian candidate
3. physical Persian-keyboard -> English candidate
4. later phases: generalized Finglish/transliteration candidates
5. later phases: spelling/normalization candidates

### Statistical language model

Runtime uses compact character 2-gram and 3-gram profiles.

The model is generated at build time from:

- dictionary-en 4.0.0
- dictionary-fa 2.0.0

The exact source word lists are not packaged as the runtime decision engine.
Runtime decisions can therefore score previously unseen word shapes.

### Holdout contract

Dictionary words are deterministically split by FNV-1a hash:

- buckets 0..1: holdout only
- buckets 2..3: threshold calibration only
- buckets 4..19: model training

The holdout evaluator therefore measures generalization against exact words
that were not used to train or calibrate the statistical profile.

### Dictionaries become priors, not gates

Existing curated word sets remain temporarily as high-precision safety priors.
They are no longer the only route to a correction and a sufficiently strong
statistical margin can override a dictionary prior.

## Important ambiguity rule

No engine can safely infer every isolated token from keyboard geometry alone.

Example:

- `سعد` can be a legitimate Persian name.
- the same physical keys can map to `sun`.

So the final system must use context rather than blindly flip every token.

## v4.7 phases

### Phase A — this PR

- statistical Persian/English language-shape model
- dictionary-independent runtime path
- short-token support
- thousands of holdout evaluations
- false-positive gate
- no Store publication

### Phase B

- sentence/field context scoring
- observed keyboard-event layout evidence
- page/field/browser language priors
- ambiguity resolution

### Phase C

- generalized Finglish beam transliteration
- Persian spelling/normalization candidate generation
- unified candidate ranking

### Phase D

- Smart Auto mode
- auto-apply only at very high confidence
- immediate local Undo
- medium-confidence cases remain suggestions
- no automatic form submission

## Privacy

The statistical profiles are bundled locally.
No developer-operated keystroke backend is introduced by this milestone.


### Tiny-word calibration

Three-character words have much less character-ngram evidence than four-character
words. v4.7 therefore calibrates them in a separate `tiny` bucket instead of
sharing one threshold with four-character words.

Thresholds are selected from calibration data to maximize wrong-layout recall
subject to a source-language false-positive ceiling. The explicit `dog` probe
is not inserted into a runtime word list; it remains a generalization test.


### Phase B implementation evidence

Context Intelligence adds local ambiguity resolution without turning page
language into a blind conversion switch.

Signals:

- text before and after the current token
- field `lang` and `dir`
- page language/direction
- browser language as a weak prior
- recent real `keydown` script + physical-key evidence for the same editable

Safety rules:

- isolated ambiguous valid-language tokens remain unchanged
- same-language context protects the source token
- opposite-language context must be strong
- the physical-layout candidate must remain statistically plausible
- no form submission or navigation is introduced

Acceptance example:

- isolated `سعد` -> unchanged
- Persian context `نام سعد بسیار معروف است` -> unchanged
- English context `bright سعد today in the sky` -> `bright sun today in the sky`


### Phase C implementation evidence

Generalized Finglish is no longer limited to `WORD_MAP`.

The runtime:

1. tokenizes Latin Finglish into one- and two-character transliteration units
2. generates Persian candidates with a bounded beam
3. ranks candidates with the local Persian statistical language model
4. combines ranking with Phase B context priors
5. protects strong English sources
6. keeps `WORD_MAP` only as a compatibility prior/fallback

Persian normalization is a separate deterministic candidate layer:

- Arabic Yeh -> Persian Yeh
- Arabic Kaf -> Persian Kaf
- Unicode NFC
- Tatweel removal
- generalized `می / نمی` ZWNJ normalization

The evaluation loader executes the complete v4.7 runtime dependency chain:
language profiles -> keyboard layout -> context -> transliteration ->
normalization -> logic.


### Phase D implementation evidence

Smart Auto applies only corrections classified as high confidence.

Policy:

- explicit user dictionary: auto
- deterministic Persian normalization: auto
- keyboard-layout intent: auto only above a strict confidence threshold
- context-resolved layout: requires strong opposite-language context
- generalized Finglish: requires strong Persian context, candidate rank separation,
  strong Persian target coverage and a source that does not look like ordinary English
- legacy WORD_MAP: suggestion-only compatibility prior

Timing:

- after a delimiter, high-confidence correction may apply quickly
- otherwise Smart Auto waits for a short typing idle interval
- explicit selections are never auto-applied

Undo:

- every automatic replacement uses the existing verified token-local mutation path
- a visible local «برگردان» action is shown immediately
- Undo suppresses immediate automatic reapplication
- no form submission or navigation is introduced

Smart Auto is enabled by default during the v4.7 candidate milestone and can be
disabled in Settings.


#### Phase D source-intent refinement

Threshold-only discrimination could not simultaneously achieve safe
unknown-English behavior and useful automatic Finglish recall.

The final Phase D candidate therefore adds a local build-time
Finglish-vs-English source-intent model:

- hashed character n-grams (2..5)
- hashed feature bins
- no raw runtime training word list
- Train split: salted buckets 20..99
- Calibration split: salted buckets 10..19
- Calibration constraint: Wilson 95% upper English false-positive bound <= 1%
- Blind evaluation split: salted buckets 0..9
- English lexical hashes remain an additional safety prior, not the decision engine

Locked v6.2 architecture probe:

- calibration exact-auto recall: 66.9875%
- calibration observed English FP: 0.7038%
- calibration Wilson upper 95%: 0.9818%
- blind exact-auto recall: 67.4375%
- blind lexical-miss English FP: 0.7912%

Context-resolved keyboard-layout auto-application additionally requires the
Phase A statistical AUTO preference.


#### Confidence contract: correctness is not the same as automatic eligibility

Phase D deliberately separates correction correctness from automatic mutation.

A token may be resolved correctly by the generalized Finglish engine while
remaining suggestion-only if the independent source-intent safety model does
not classify the Latin source as sufficiently Finglish-like.

Example:

- `baran` is resolved to `باران`
- the locked v6.2 source-intent score for this token is below the conservative
  automatic threshold
- therefore it remains a suggestion instead of being forced into Smart Auto

This is intentional. The product must not lower a global safety threshold or
hard-code an acceptance exception to make a single demonstration token
automatic.

Automatic Finglish quality is evaluated as an aggregate locked blind gate:

- exact Auto recall >= 30%
- unknown-English lexical-miss Auto false positives <= 1%

The locked v6.2 blind architecture probe achieved approximately 67.44% exact
Auto recall and 0.79% lexical-miss English false positives.


#### Phase D runtime arbitration correction

The v8.1 attrition diagnostic identified the release-blocking runtime problem:

- Phase C exact Finglish selection: 6305 / 7923
- source-intent preferred among those exact candidates: 5341
- smart_farsi_converter exact result: only 478
- full runtime exact Auto: only 316
- lexical-prior Auto attrition: only 2 cases

The loss was therefore not caused by the English lexical prior or by the
source-intent classifier. It was caused by candidate arbitration:
smart_farsi_converter evaluated physical keyboard layout before generalized
Finglish, so many Latin Finglish inputs were converted into unrelated Persian
keyboard-layout strings before Smart Auto could evaluate the correct Phase C
candidate.

The corrected arbitration rule is narrow:

1. explicit user dictionary remains higher priority
2. known-English lexical safety remains higher priority
3. for a Latin token, if the independent generalized Finglish candidate passes
   the already-locked strong Persian-context + source-intent Auto gate, it may
   preempt a conflicting physical-layout interpretation
4. all remaining inputs continue through the existing layout / context-layout /
   Finglish suggestion pipeline

No token-specific runtime exception is added.
