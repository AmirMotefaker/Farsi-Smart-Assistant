# v4.6.0 — Bidirectional Keyboard Intent Correction

## Product decision

Chrome Web Store and Firefox AMO publication is paused until the product is complete enough for public distribution.

The core wrong-layout correction must be bidirectional:

- English keyboard active + Persian intent: `sghl -> سلام`
- Persian keyboard active + English intent: `هقشد -> iran`

Both directions use the same inline suggestion/editing flow. v4.6.0 does not silently replace text without the existing user-control surface.

## Why v4.5.1 was insufficient

The physical Persian-to-English mapping already existed, but reverse confidence was effectively limited to a small curated English-word set. A valid mapped candidate such as `iran` received no confidence when it was outside that set.

## v4.6.0 confidence model

Reverse correction combines:

1. deterministic physical-key mapping
2. exact high-confidence English evidence
3. English word-shape evidence
   - minimum length
   - vowel presence and ratio
   - common English bigram density
   - rare-cluster penalty
4. Persian-source protection
   - exact high-confidence Persian vocabulary
   - Persian bigram-density signal

A generic reverse correction is accepted only when English evidence is strong and Persian-source evidence is weak.

## Real-browser controlled-input gate

The first Chrome manual gate proved that reverse intent detection works but
exposed an application-path defect on a live Google field: the suggestion
was shown, while accepting it did not reliably commit the replacement.

The fix makes standard INPUT/TEXTAREA replacement controlled-input aware:

- native prototype value setter first
- bubbling replacement input event
- post-mutation value verification
- browser-native insert fallback only when needed
- failed application triggers a fresh live-field suggestion check instead of
  silently hiding the action

This behavior is release-blocking and must pass a second real-browser gate.


## document_idle / autofocus integration fix

A second real-Chrome gate showed that the exact v4.6.0 engine could pass all
converter/application tests yet fail to show a suggestion on Google Search.

Root cause: the content script runs at `document_idle`, while editable
tracking previously began only after a `focusin` observed by the content
script. Pages may focus their primary search field before that listener exists.

The integration fix adds:

- bootstrap tracking for `document.activeElement`
- document-level capture fallback for the first `input` event on an
  untracked editable
- retained per-element input/select tracking after registration
- regression coverage for pre-focused INPUT, pre-focused TEXTAREA and
  dynamically encountered editables

This is release-blocking and requires a new real-Chrome gate.
